## 2. Вариант 15 — предметная область

### 2.1. Формулировка (ключевые требования варианта)

> В университете учатся **студенты** по **образовательным программам**. Выпускающие подразделения разрабатывают **учебные планы** (перечень дисциплин с семестрами, часами, ЗЕТ и видами аттестации; за реализацию дисциплины отвечает **кафедра**). В **АНОК** учебные планы проверяются на соответствие требованиям **ФГОС**. План подписывают руководитель выпускающего подразделения, начальник АНОК и проректор по учебной работе. На **учёном совете** учебные планы утверждаются и подписываются **ректором**; утверждение происходит **ежегодно**. До начала семестра изменения оформляются **служебными записками**, которые подписывают руководители выпускающего и реализующего подразделений; АНОК вносит изменения в план и **повторно проверяет** его на соответствие ФГОС.

### 2.2. Жизненный цикл учебного плана

```
1. Выпускающее подразделение РАЗРАБАТЫВАЕТ учебный план
   (дисциплины + вид аттестации + семестр + кафедра-исполнитель)
        │
        ▼
2. АНОК ПРОВЕРЯЕТ план на соответствие ФГОС ──► НеСоответствует ──► доработка
        │  Соответствует
        ▼
3. ПОДПИСИ: руководитель выпускающего подразделения,
   начальник АНОК, проректор по учебной работе
        │
        ▼
4. УЧЁНЫЙ СОВЕТ УТВЕРЖДАЕТ план, подписывает РЕКТОР
   (утверждение происходит ежегодно)
        │
        ▼
5. До начала семестра — ИЗМЕНЕНИЯ:
   служебная записка (подписывают руководитель выпускающего
   и руководитель реализующего подразделения)
        │
        ▼
6. АНОК вносит изменения в план и ПОВТОРНО проверяет на ФГОС
```

### 2.3. Роли пользователей (перечисление `РолиПользователей`)

Администратор · РуководительВыпускающегоПодразделения · РуководительРеализующегоПодразделения · СотрудникАНОК · ПроректорПоУР · Ректор

## 5. Аудит структуры: непротиворечивость и логичность

Проверено 2026-09-21: структура из `ЛР1_Проектирование_структуры.md` сверена с `ЛР2_Создание_объектов_пошагово.md`, UML-диаграммой (`UML(4)-ДК.drawio.pdf`) и формулировкой варианта 15 — по всем объектам, реквизитам, типам и связям.

**Вердикт: структура непротиворечива и логична после 5 исправлений** (все они уже внесены в `ЛР1_*`, `ЛР2_*` и в §4 этого README). Каждый объект и каждое поле выводятся из требований варианта или из UML; жизненный цикл плана покрыт объектами полностью; числа сходятся (34 объекта, минимумы ЛР1 превышены в каждой позиции).

### 5.1. Найденные противоречия и их устранение

| # | Где | Было (противоречие) | Стало (канон) | Почему |
|---|---|---|---|---|
| 1 | Перечисление `РолиПользователей` | 5 значений в ЛР1 vs 6 в ЛР2 (в ЛР1 отсутствовал `РуководительРеализующегоПодразделения`) | **6 значений** (единообразно везде) | UML: служебную записку подписывают руководитель выпускающего **и реализующего** подразделений — без этой роли вторую подпись не выразить |
| 2 | Регистр `ИсторияСтатусовУчебныхПланов` | одновременно «режим: независимый» **и** «Регистраторы: УчебныйПлан, ПроверкаФГОС, УтверждениеУчебногоПлана» — у независимого регистра регистраторов не бывает | периодический, **независимый**; «регистраторы» → **документы-источники**, пишущие наборы записей **кодом проведения** (ЛР5): `УчебныйПлан`, `ПроверкаФГОС`, `УтверждениеУчебногоПлана`, `СлужебнаяЗаписка` | Независимый режим нужен для ручного ввода истории на ЛР2; автоматизация не теряется — приходит кодом на ЛР5 |
| 3 | Регистр `РезультатыПроверокФГОС` | ЛР1: «подчинён регистратору» (регистратор `ПроверкаФГОС`) vs ЛР2: «Независимый» | периодический, **независимый**; пишет код проведения `ПроверкаФГОС` (ЛР5) | Тот же аргумент: на ЛР2 заключения АНОК вводим руками (3 записи); для независимого регистра конструктор движений не применим — пишем кодом |
| 4 | Поле `Замечания` регистра `РезультатыПроверокФГОС` | `Строка (0)` в ЛР1 vs `Строка, 1000` в ЛР2 | **Строка (1000)** | Единый тип. В документе `ПроверкаФГОС.Замечания` — неограниченная строка; при записи в регистр обрезаем `Лев(Замечания, 1000)` (правило ЛР5) |
| 5 | ТЧ `Изменения` документа `СлужебнаяЗаписка` | есть `НовыеЧасы`, `НовыйВидАттестации`… но **нет `НовыйЗЕТ`**, хотя ЗЕТ учитывают и план, и оба регистра накопления | добавлена колонка **`НовыйЗЕТ` (Число 5,2)** | Без неё изменение часов/ЗЕТ нельзя согласованно отразить в `ОбъемЧасовПоПрограммам` и `НагрузкаКафедр` (ресурс ЗЕТ) и в строках плана |

### 5.2. Решения проектирования — почему это логично, а не случайность

| Решение | Обоснование |
|---|---|
| `УчебныйПлан` — документ, а не справочник | у него дата, номер и жизненный цикл во времени (создан → проверен → подписан → утверждён) |
| Семестр/часы/ЗЕТ/аттестация — в ТЧ плана, а не в справочнике `Дисциплины` | одна дисциплина в разных планах имеет разные часы и семестры — это свойство связи «план–дисциплина», а не самой дисциплины |
| `Подразделения` — один справочник с `ТипПодразделения` | структура (наименование, институт, руководитель) одинакова для выпускающих подразделений, кафедр и администрации |
| Взаимные ссылки `Подразделения` ↔ `Сотрудники` (руководитель) | реальная ситуация «подразделение ↔ руководитель»; создаётся в два прохода (ЛР2, шаги 5.1–5.3) — не сбой, а штатный приём |
| Оба регистра сведений — независимые | требование ЛР2 (ручной ввод 3–5 записей); автоматизация — кодом проведения на ЛР5 (см. §5.1, №2–3) |
| Регистры накопления — вид «Остатки» | планы не только прибавляются, но и уменьшаются (служебной запиской) — приход/расход отвечают «сколько часов заложено в программу сейчас» |
| Изменения — только документом `СлужебнаяЗаписка`, а не правкой плана | так требует предметная область: 2 подписи → АНОК → внесение → повторная проверка ФГОС; событие с датой и номером, а не тихая правка |
| UML-класс `Пользователь` (логин, пароль) → `Сотрудники` + `РолиПользователей` без логина/пароля | авторизация в учебной версии — платформенная (пользователи ИБ); отдельной сущности «учётка» не храним, роль — реквизит `РольПользователя` |
| Поле `УчебныйПлан.ФГОС` намеренно дублирует `ОбразовательнаяПрограмма.ФГОС` | план фиксирует ФГОС, **по которому его проверяли** (аудит); согласованность гарантирует правило R1 |
| Ресурсы регистра (`Подписант`, `Проверил`, `Замечания`) — «что храним», измерение `УчебныйПлан` — «по кому строка» | классическое разделение регистров сведений; период записи даёт «когда» — получается журнал «кто, когда, что» |

### 5.4. Машина статусов (жизненный цикл определён полностью — без «висячих» состояний)

**`СтатусыУчебногоПлана`:**

```
Черновик ──отправка на проверку──► НаПроверкеВАНОК
НаПроверкеВАНОК ──ПроверкаФГОС: Соответствует──► СоответствуетФГОС
НаПроверкеВАНОК ──ПроверкаФГОС: НеСоответствует──► Черновик (на доработку)
СоответствуетФГОС ──проставлены все 3 подписи──► Подписан
Подписан ──УтверждениеУчебногоПлана (протокол, ректор)──► Утвержден
Утвержден ──СлужебнаяЗаписка: ИзмененияВнесены──► НаПроверкеВАНОК (повторная проверка ФГОС)
```

**`СтатусыСлужебнойЗаписки`:**

```
Подготовлена ──подписи 2 руководителей──► ПодписанаРуководителями
ПодписанаРуководителями ──принята АНОК──► ПринятаАНОК
ПринятаАНОК ──изменения внесены в план──► ИзмененияВнесены
Подготовлена / ПодписанаРуководителями ──отказ──► Отклонена
```

Каждый переход фиксируется в `ИсторияСтатусовУчебныхПланов` (кто, когда, какой статус). Каждое из 5/5 значений перечислений используется в хотя бы одном переходе — «мёртвых» значений нет.

### 5.5. Матрица движений «документ → регистр» (без пробелов и дублей)

| Документ (при проведении) | `ИсторияСтатусовУчебныхПланов` | `РезультатыПроверокФГОС` | `ОбъемЧасовПоПрограммам` | `НагрузкаКафедр` |
|---|---|---|---|---|
| `УчебныйПлан` | + статус плана | — | + приход (часы, ЗЕТ по семестрам) | + приход (часы, ЗЕТ по кафедрам) |
| `ПроверкаФГОС` | + статус плана | + результат, проверил, замечания | — | — |
| `УтверждениеУчебногоПлана` | + статус «Утвержден» | — | — | — |
| `СлужебнаяЗаписка` | + план → на повторную проверку | — | ± приход/расход (по `ТипИзменения`) | ± приход/расход (по `ТипИзменения`) |

Каждый из 4 регистров получает данные хотя бы от одного документа, у каждого «+/-» есть источник — требование ЛР5 «автоматическая запись во все регистры» покрыто целиком (РН — движениями/конструктором, РС — наборами записей кодом проведения).

### Типовые проблемы

| Симптом | Причина и лечение |
|---|---|
| В поле «Тип» не находится нужный объект | Объект ещё не создан — проверьте порядок создания (этапы идут сверху вниз) |
| Конфигуратор ругается на имя объекта | Пробел или имя не с буквы — имена слитно, каждое слово с большой буквы |
| Регистр сведений не даёт «Создать» | Режим записи «Подчинение регистратору» — для ручного вода нужен «Независимый» |
| Панель разделов пустая | У подсистем не заполнен «Состав» |
| Изменил объект, а в Предприятии ничего не поменялось | Забыли `F7` |
| `НачалоВыбора` показывает весь список | Не отключили стандартную обработку (`СтандартнаяОбработка = Ложь`) |
| Отчёт СКД падает при пустом параметре | Снять «Ограничение доступности» + включить пользовательскую настройку + значение по умолчанию |
| Реквизит формы «забывается» после закрытия | Так и должно быть: реквизиты формы не сохраняются в БД |

### Ключевые «почему» для защиты (полный список — в `ЛР1_*.md`, раздел 6)

1. `УчебныйПлан` — документ, а не справочник: у него дата, номер и жизненный цикл во времени.
2. Семестр/часы/аттестация — в ТЧ плана, а не в справочнике `Дисциплины`: одна дисциплина в разных планах имеет разные часы и семестры (свойство связи «план–дисциплина»).
3. Подразделения — один справочник с реквизитом `ТипПодразделения`: структура одинаковая, различается только тип.
4. Регистр сведений хранит ИСТОРИЮ статусов/проверок, а документ — только текущее состояние (аудит подписей).
5. Регистры накопления — чтобы итоги (часы, ЗЕТ) считались автоматически при проведении.
6. Изменения — только через `СлужебнаяЗаписка`: две подписи, внесение АНОК, повторная проверка ФГОС; событие с датой и номером, а не «правка руками».
